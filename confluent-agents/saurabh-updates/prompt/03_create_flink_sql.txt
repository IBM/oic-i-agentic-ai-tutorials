In the confluent-agents project, create or update run_flink_sql.py to submit Flink SQL statements via the Confluent Cloud Flink SQL REST API. Load all credentials from .env using python-dotenv. Use exactly these variables: FLINK_API_KEY, FLINK_API_SECRET, CONFLUENT_ORG_ID, CONFLUENT_ENVIRONMENT_ID, CONFLUENT_FLINK_COMPUTE_POOL_ID, CONFLUENT_CLUSTER_ID. Set sql.current-catalog to CONFLUENT_ENVIRONMENT_ID and sql.current-database to the Kafka cluster name — this is NOT the cluster ID (which looks like lkc-xxxxx) but the display name of the cluster (for example "cluster_0"). Add a CONFLUENT_CLUSTER_NAME variable to .env.example with placeholder value <YOUR_CLUSTER_NAME> and load it from .env alongside the other variables.

Perform the following steps in order. Do NOT skip Step 0.

### Step 0 — Stop stale streaming jobs from any previous run

Call GET on https://flink.us-east-2.aws.confluent.cloud/sql/v1/organizations/{ORG_ID}/environments/{ENV_ID}/statements, following pagination via the response's metadata.next field until there is no next page. From the full list, find every statement whose name starts with "insert-availability-" and whose status.phase is RUNNING or PENDING. For each one found, call DELETE on that same statements URL plus /{statement_name} to stop it. Print which statements were stopped, or print that none were found.

This step is required every run, not optional: DROP TABLE does not cancel a running persistent streaming statement from an earlier run. Skipping this step leaves old jobs running, which causes inconsistent, duplicated numbers in inventory.availability that look like random bugs but aren't.

### Step 1 — Create the tables and streaming job

Submit the following SQL statements in this exact order, polling each until COMPLETED or RUNNING before submitting the next:

DROP TABLE IF EXISTS `inventory.transactions`;
CREATE TABLE `inventory.transactions` (
  sku              STRING,
  branch           STRING,
  quantity         BIGINT,
  transaction_type STRING
)
DISTRIBUTED BY HASH(sku, branch) INTO 6 BUCKETS;

DROP TABLE IF EXISTS `inventory.availability`;

CREATE TABLE `inventory.availability` (
  sku                STRING,
  branch             STRING,
  available_quantity BIGINT,
  PRIMARY KEY (sku, branch) NOT ENFORCED
)
DISTRIBUTED BY HASH(sku, branch) INTO 6 BUCKETS;

INSERT INTO `inventory.availability`
SELECT
  sku,
  branch,
  SUM(
    CASE
      WHEN UPPER(transaction_type) = 'ADDITION' THEN quantity
      WHEN UPPER(transaction_type) = 'SALE'     THEN -quantity
      ELSE 0
    END
  ) AS available_quantity
FROM `inventory.transactions`
GROUP BY sku, branch;

Submit each statement separately and poll until it reaches COMPLETED or RUNNING status before submitting the next. The DROP statements will reach COMPLETED quickly. The INSERT INTO statement will reach RUNNING and stay there — that is correct, it is a continuous streaming job. Print the status of each statement. Never print API secrets.

CRITICAL — do not modify the inventory.transactions CREATE TABLE statement above. Specifically, do NOT add a WITH (...) clause to it, and do NOT add 'value.format', 'key.format', or 'connector' options. Leave it exactly as written. Confluent Cloud Flink auto-creates the topic and auto-registers a compatible schema when there is no WITH clause. Adding a WITH clause with json-registry or avro-registry formats will break the pipeline unless a matching schema is separately pre-registered in Schema Registry, which this tutorial does not do.
